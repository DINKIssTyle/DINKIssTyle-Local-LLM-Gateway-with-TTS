# JEV 스킬 선택 검증 — 2026-10-10

현재의 `EmbeddingGemma 2 text-vision 440M` + MediaPipe DecisionMaker는 스킬 선택을 약 33ms에 수행하지만, 이 평가에서는 필요한 스킬을 빠뜨렸다. **단독 선택 또는 스킬 제외 기준으로 적용하지 않고 기존 주 LLM의 판단을 유지한다.** 운영 코드·모델 설정·사용자 DB는 변경하지 않았다.

## 평가 구성

- 실제 설치 카탈로그: 내장 `msn-weather-current`, `python-calculator` 두 개. 사용자 스킬 디렉터리에는 README만 있었다.
- 사람이 작성한 요청 60개: 개발 문항 16개, 평가 문항 44개. 현재 날씨 조회, 정확한 수치·날짜 계산, 스킬 불필요, 두 스킬 동시 필요를 균형 있게 구성했다. 명시적 호출 8개와 최근 대화가 필요한 후속 질문 4개도 포함했다.
- 영어·한국어, 같은 단어가 등장하지만 조회·계산은 필요 없는 요청, 다른 주제의 개인 메모리 질문을 포함했다. 후속 질문은 최근 대화와 현재 요청을 함께 전달했다.
- 세 방식 각각 3회, 고정 시드로 순서를 섞어 총 540회 평가했다. 이는 독립적인 요청 540개가 아니라 **60개 요청의 반복 측정**이다. 세 반복의 선택 결과는 모두 같았다.
- 기대 스킬은 평가 전에 작성했다. 운영 중 주 LLM의 답변을 정답으로 삼거나 별도 LLM을 호출하지 않았다. 어떤 스킬의 도구도 실행하지 않았다.
- 실행 환경: Python 3.12.10, mediapipe 1.1.0, macOS arm64. 로컬 모델만 사용했으며 API 키나 새 모델 다운로드가 필요하지 않았다.

`cases.json`은 기대 답안과 요청, `result-2026-10-10.json`은 각 실행의 선택·확률·시간과 집계, `scripts/eval-jev-skills.py`는 재실행 스크립트다. 실제 스킬 설명과 평가 문항의 SHA-256을 결과에 기록했다.

## 결과

평가 문항 44개의 결과다. 정확도는 필요한 스킬 **집합 전체**가 맞았을 때만 인정한다. 예를 들어 두 스킬이 필요한데 하나만 고르면 오답이다. 반복 결과가 같으므로 아래 개수는 고유 문항 기준이다.

| 방식 | 정확한 선택 | 정확도 | 명시 호출 우선 규칙 적용 후 | 시간 중앙값 / p95 |
|---|---:|---:|---:|---:|
| 실제 영어 설명으로 4개 분류: 없음 / 날씨 / 계산 / 둘 다 | 31/44 | 70.5% | 33/44, 75.0% | 33.3ms / 34.5ms |
| 한국어 설명으로 같은 4개 분류 | 28/44 | 63.6% | 30/44, 68.2% | 33.3ms / 34.6ms |
| 스킬마다 필요 여부를 독립 Boolean 판단, 기본 임계값 0.5 | 11/44 | 25.0% | 12/44, 27.3% | 66.4ms / 68.9ms |

시간은 준비된 세션의 SDK 호출만 측정했다. Boolean 방식은 두 스킬의 호출 시간을 합쳤다. Go IPC, 주 LLM, 초기 import와 모델 준비 시간은 포함하지 않았다. 결정 세션 생성은 약 397ms, Choice 사전 준비는 영어 약 329ms·한국어 약 134ms였다. 실행 오류와 2초 초과는 없었다.

가장 좋은 영어 Choice에 기존 앱과 같은 명시 호출 우선 규칙을 적용한 결과:

| 기대 작업 | 정확한 선택 |
|---|---:|
| 스킬 필요 없음 | 8/9 |
| 날씨만 | 11/12 |
| 계산만 | 9/12 |
| 두 스킬 모두 | 5/11 |

필요한 스킬의 재현율은 73.9%(34/46)였다. 재현율의 분모는 요청 수가 아니라 필요한 개별 스킬 수다. 한국어 요청만 보면 영어 Choice의 원래 정확도는 21/29, 영어 요청은 10/15였다. 단순한 번역으로 해결되는 문제는 아니었다.

대표 오류:

- `인천 현재 바람 상태를 확인하고, 별도로 30의 팩토리얼을 구해줘.` → 날씨만 선택. 계산 스킬 누락.
- `기온 측정값 12, 15, 19, 23의 평균과 표준편차를 구해줘. 웹 조회는 필요 없어.` → 스킬 없음. 계산 스킬 누락.
- `Calculate the number of days between 2024-02-28 and 2024-03-03.` → 스킬 없음. 계산 스킬 누락.
- `Summarize this sentence: The date calculator app displays weather icons.` → 두 스킬 모두. 단어의 등장과 실제 작업 의도를 혼동.
- `$msn-weather-current $python-calculator ...` → JEV만 쓰면 한 스킬을 빠뜨린 사례가 있었다. 명시 호출은 모델 결과와 관계없이 서버 규칙으로 보존해야 한다.

## 후보 유지 방식의 보충 분석

오류를 본 뒤 진행한 탐색 분석이며 별도의 독립 검증이 아니다. 가장 높은 분류 확률이 0.90 미만이면 두 스킬을 모두 주 LLM에 전달하고, 이상이면 선택 결과를 후보로 쓰되 명시 호출을 추가했다. 이 값은 SDK의 `confidence`와 다르며, 실제 정답 확률로 검증된 값도 아니다.

영어 Choice는 평가 문항에서 필요한 스킬을 모두 후보에 남겼지만, 44개 중 33개(75%)에는 여전히 두 스킬을 제공해야 했다. 평균 후보 수는 2개에서 약 1.70개로 줄었다. 이는 후보 개수의 감소이며 실제 프롬프트 토큰·전체 응답 시간 절감을 뜻하지 않는다. 한국어 Choice는 이 방식에서도 필요한 스킬 한 개를 누락했다.

두 스킬뿐인 현재 구성에서는 매 요청마다 약 33ms를 추가하면서 스킬 설명을 일부 줄이는 이득이 제한적이다. 실제 전체 응답 시간이나 주 LLM과의 정확도 비교는 측정하지 않았다. 스킬이 늘어나면 명시 호출을 보존하고 JEV를 후보 순서에만 활용하는 실험을 새 문항으로 검증할 수 있다. 이번 결과로 자동 스킬 차단이나 운영 라우팅을 활성화하지 않는다.

## 재실행

프로젝트 루트에서 검증에 사용한 기존 로컬 환경으로 실행한다. 경로는 개발 검증 환경이며 앱 설치 경로와 다르다.

```sh
MPLCONFIGDIR=/private/tmp/dkst-jev-runtime/mpl \
  /private/tmp/dkst-jev-runtime/bin/python -B scripts/eval-jev-skills.py \
  --model /private/tmp/dkst-jev-runtime/embeddinggemma-2-text-vision-440m.litertlm \
  --output evals/jev-skills/result-2026-10-10.json
```

질문 구성·확률 임계값을 조정한다면 이번 평가 문항의 결과로 일반화 성능을 주장하지 말고 새 문항을 작성해 다시 평가한다.
